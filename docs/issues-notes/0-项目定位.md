- DevAgentOps：面向 CI/CD 诊断场景的 AI Agent 控制平面，诊断并输出包含证据的报告。
- 系统基于“评测与坏案驱动开发 (Evaluation & Badcase-Driven Development)”理念设计
- 通过底层 TDD 确保运行时框架稳定性。
- 通过顶层 Eval 基线与 Badcase 归因实现 Agent 智能的可量化持续迭代。

## 项目意义
##### 为什么做这个项目，解决了什么问题？
这个项目同时解决了一个“业务痛点”和一个“工程痛点”**：

1. **业务痛点：研发日常的“流水线排查地狱”**
    
    - **问题**：在企业日常开发中，CI/CD 流水线（编译、测试、构建）失败是极高频事件。研发人员往往需要耗费半小时甚至几小时，去翻看几千行的报错日志，再去交叉比对代码库、搜寻历史 Issue，才能找到真正的 Root Cause（比如某个隐蔽的依赖冲突或偶发超时）。
        
    - **解决**：DevAgentOps 提供了一个智能排查流水线。它能自动获取日志、检索代码库和历史工单，最终输出一份结构化的诊断报告，直接指出报错代码行和修复建议，将排查时间从小时级缩短到分钟级。
        
2. **工程痛点：Agent 落地缺乏“评测与观测（Ops）底座”**
    
    - **问题**：现在业界做 Agent 大多停留在“跑通一次 Demo”的阶段。一旦上线，如果 Agent 产生幻觉、掉进死循环、或者因为底层模型微调导致性能退化，开发者完全是两眼一抹黑，不知道怎么排查和优化。
        
    - **解决**：这就是 DevAgentOps 中 Ops 的价值。它不仅仅是一个排查工具，更是一个**“评测与坏案驱动（EBDD）”的控制平面**。它通过冻结组件指纹、全链路 Trace 记录、多维指标打分（Metric Vectors），解决了大模型应用**“不可控、不可溯源、无法量化回归”**的核心工程难题。

##### 为什么不直接用现有的agent来应对这个场景？
1. **安全与权限边界（不适合企业级排查）**
    - 像 Devin 或 Claude Code 这类编码 Agent，其核心目标是**“自动写代码并修改提交（Mutation）”**。但在企业的 CI/CD 和生产排查场景中，直接让黑盒 Agent 去修改配置、重启服务或提交 PR 是极其危险的。
        
    - DevAgentOps 严格限制了操作边界，我们设计了**工具权限沙箱（Tool Policy Sandboxing）**，明确区分了“只读诊断”和“修改操作”，杜绝了 Agent 的越权破坏。
        
2. **框架黑盒与评测缺失（无法做闭环迭代）**
    
    - 如果直接拿 LangChain 或第三方成型 Agent 来做，它们隐藏了大量的中间状态（隐藏的 Chain-of-Thought）。当 Agent 诊断错误时，我无法精确定位是因为 RAG 没搜到、还是工具参数传错了。
        
    - 我自研了 V1 的轻量 Runtime Baseline，是为了实现**绝对的数据透明和 A/B 评测对齐**。它能将 Agent 跑过的每一步打上指纹并记录进 SQLite，从而生成精准的 Badcase 报告。这是那些“开箱即用”的通用 Agent 给不了的底座能力。
        
3. **缺少垂直领域的业务抽象（MCP 与 Skill Registry）**
    
    - 通用 Agent 主要是“代码生成器”，它们并不懂企业内部复杂的 DevOps 生态。
        
    - DevAgentOps 引入了专门的组件注册表（Component Registry），可以针对性地封装获取日志、比对测试用例等垂直能力，未来还可以无缝扩展对接各种研发平台的系统。
